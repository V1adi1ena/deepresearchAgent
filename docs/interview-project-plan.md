# Deep Research Agent 求职修改计划与目标简历

日期：2026-10-23

状态：方案已确认，尚未实施本计划。本文件中的目标简历描述方案完成后的版本，不代表当前功能全部完成。

## 目标与取舍

求职方向为通用后端为主、兼顾 AI 应用。本项目作为 Python AI 辅项目，围绕三条已有技术主线形成可演示、可解释、可验证的能力：

1. 依赖驱动的异步编排、局部失败处理与增量重规划。
2. 共享研究记忆、语义检索去重与预算约束下的上下文压缩。
3. 基于证据的 Red-Blue 审查、补充检索与定向修复。

评测用于解释这些机制的收益和代价，结果不预设为完整系统一定更好。不填写未经实际测量的成功率、性能提升或效果指标。

| 原有内容 | 决策 | 理由 |
| --- | --- | --- |
| DAG、状态机、并发限制、重规划与降级 | 保留并优先修复 | 可以深入解释任务依赖、数据流、失败传播和结果复用 |
| Embedding、TextRank、分级压缩 | 保留并接入真实研究上下文 | 通过预算、信息保留与处理开销讨论取舍 |
| SQLite、NumPy 共享记忆及语义检索去重 | 保留，合并进上下文主线 | 说明中间结果如何共享和复用，而非单独罗列存储组件 |
| 启发式冲突检测与自动消解 | 暂不升级，不作为主要简历亮点 | 当前能力边界较窄，不承诺通用事实冲突识别或多数投票保证事实正确 |
| Red-Blue 审查与修复 | 保留，集中于可核对的事实和引用问题 | 需要展示具体证据、修改依据、误修改和额外成本 |
| ResearchBench、消融实验 | 保留并修正 | 为设计选择提供证据 |
| JSON 解析降级 | 保留为实现细节 | 不单独使用未经验证的 85% 到 95% 指标 |
| FastAPI、SSE、任务平台和断点续跑 | 本轮不新增 | 避免挤占核心机制修复与验证时间 |
| 自进化、训练、多模态 | 不纳入本轮求职目标 | 与当前三条主线无直接依赖 |

不因本计划自动删除现有模块。暂不展示的功能与需要删除的代码分别判断。

## 实施顺序与验收

按 P0 → P1 → P2 → P3 → P4 推进。每阶段先复现关键问题，再做必要修改并验收；未通过的阶段不标记完成。

### P0：修正入口和评测基础

目的：让后续实现与实验能够复现，防止使用错误指标判断模块价值。

- [ ] 确认并记录一套实际可用的安装、单条运行及离线测试命令，修正过期入口。
- [ ] 统一事实指标、综合权重与输出字段；避免因字段缺失而静默漏计。
- [ ] 使用答案错误、否定和引用不支持结论等反例检查指标边界；词语命中不能直接命名为事实正确。
- [ ] 使记忆与压缩开关真正控制执行路径，并验证关闭后没有相关调用。
- [ ] 正式实验记录 embedding 后端、模型、配置与是否存在模拟或降级；关键能力不可用时，不继续输出可用于效果结论的正常分数。

主要涉及：`src/core/runner.py`、`src/core/ablation.py`、`evaluation/metrics/rule_based.py`、`evaluation/benchmarks/research_bench.py`、现有运行及测试入口。

验收：错误答案不能仅因命中事实名称获得满分；评分字段一致；开关关闭确实改变调用；文档中的运行命令在记录的环境可执行。

### P1：做实 DAG 数据流、故障处理与重规划

- [ ] 每层结束后发布结果，在下游任务启动前完成依赖上下文构建。
- [ ] 统一 dependencies 与提示词输入的约定，不要求调用方猜测内部结果键名。
- [ ] 明确上游失败后的阻断、降级或重规划规则，避免把错误信息作为正常证据传播。
- [ ] 将成功结果保留在任务结果集合中，重规划不丢失它们，最终合成同时使用保留结果和新结果。
- [ ] 明确有界重试与重规划的区别：临时故障可重试；任务方案需要变化时才重规划；预算内不能无限叠加。
- [ ] 修复全局期限和降级合成分支，梳理同步模型调用、剩余期限与资源清理。
- [ ] 用会话、运行和任务的明确作用域管理结果标识，检查不同研究运行复用 task_id 时的持久化覆盖问题。

主要涉及：`src/orchestrator/orchestrator.py`、`src/agents/researcher.py`、`src/planner/planner.py`、模型调用边界，以及必要的记忆读写路径。

验收：

- [ ] A 的特定输出能够进入依赖它的 B 的实际提示词。
- [ ] 并发数量受配置限制；失败依赖按既定规则处理。
- [ ] 重规划保留已完成结果，且没有无必要地重复执行成功任务。
- [ ] 部分成功、全部失败、阶段超时和全局超时分别产生清楚、可解释的结果。
- [ ] 区分取消协程、停止后续调度和结束底层请求，不宣称无法兑现的强制取消能力。

面试主线：为什么需要依赖图；为什么重试与重规划不同；如何发布结果；失败如何传播；超时后哪些工作仍可能运行。

### P2：连通共享记忆与预算约束下的上下文优化

- [ ] 明确共享记忆写入、检索与复用的时机，验证会话隔离与来源保留。
- [ ] 将压缩接到实际增长的研究上下文边界，而非仅保留独立压缩器实现。
- [ ] 压缩证据内容时保留任务、来源和摘录的关联；处理消息时保持工具调用与工具结果的协议关系。
- [ ] 对语义去重保留误合并检查，不能把高相似度直接等同于相同事实。
- [ ] 在同一上下文预算下比较直接截断、相关性筛选、加入 TextRank 的策略，检查关键证据保留和开销。
- [ ] 根据实验选择分级策略，并统一代码、文档和简历描述；不为保留“三级”名称强行维持特定结构。

主要涉及：`src/memory/`、`src/compressor/`、`src/agents/researcher.py` 及实际上下文组装边界。

验收：构造包含干扰文本和必要证据的输入，能解释哪些内容保留或丢失；下游结论仍能追溯来源；实验使用真实语义 embedding，并记录实际后端。

面试主线：为什么不用直接截断；如何判断冗余；重要信息丢失如何发现；压缩额外计算是否值得；共享记忆与执行结果复用如何分工。

### P3：做实基于证据的 Red-Blue 审查与修复

- [ ] 优先针对可核对的事实和引用问题输出结构化问题，保留定位、问题类型与证据。
- [ ] 补检得到的新来源进入统一来源记录，修复后的报告引用能够对应到实际检索内容。
- [ ] 保留修改前后内容及依据；补检失败时允许删除无依据结论或标注不确定，不强制生成确定答案。
- [ ] 评分与记录绑定实际报告版本，不把修复前的评分作为修复后报告的结果。
- [ ] 设置轮数与调用预算，检查重复问题和无效修复；不能仅凭模型自评置信度证明事实正确。
- [ ] 用人工标注的错误数字、错误日期、无依据引用和本来正确的内容，检查发现、修复及误修改情况。

主要涉及：`src/adversarial/red_agent.py`、`src/adversarial/blue_agent.py`、`src/adversarial/loop.py`、来源记录与报告合成路径。

验收：能展示一条完整的“错误 → 问题定位 → 补检证据 → 修改 → 核对”记录，以及至少一个未成功修复或误修改案例。不用审查模型评分上涨直接证明事实质量提高。

面试主线：两个 Agent 的职责为什么值得拆分；修复依据来自哪里；如何避免相互附和；没有证据时如何处理；多轮审查增加多少成本。

### P4：形成可复现的实验与面试材料

- [ ] ResearchBench 区分开发题和保留测试题，记录题目来源、参考证据及评分口径。
- [ ] 对比固定检索后合成、DAG 编排、DAG 加审查；压缩作为单独变量测试。
- [ ] 比较时统一模型、可用工具和预算上限，记录实际配置与实际开销；必要时固定检索材料，减少外部搜索变化造成的干扰。
- [ ] 记录完成情况、证据支持、修复正确性与误修改、耗时、调用次数和 token 用量。实际用量与估算值分别标注。
- [ ] 保存问题级结果、报告、轨迹和失败原因；不能仅保存汇总分数。
- [ ] 整理两到三个可复现案例，说明现象、定位、备选方案、修复及局限；实验故障不写成生产事故。

验收：能根据同一组实验说明哪些机制值得默认启用、哪些无稳定收益；简历中的每项结果均可追溯到具体记录。没有测出的数字不提前填入。

### Deep Research Agent｜个人项目

**项目描述：** 面向复杂研究任务的多智能体协作系统，支持问题拆解、并行检索、研究记忆共享及带引用报告生成，通过上下文压缩与证据审查改善长链路研究过程。

**技术栈：** Python、asyncio、SQLite、NumPy、Sentence Transformers、TextRank

- **异步编排与容错：** 基于 asyncio 与 Semaphore 实现 DAG 依赖调度及并发控制，通过状态机管理规划、执行、合成与重规划；针对子任务失败和全局超时设计分级降级策略，保留成功结果并传递依赖上下文，减少重规划中的重复执行。
- **共享记忆与上下文优化：** 基于 SQLite 与 NumPy 构建跨 Agent 共享记忆，通过语义检索与去重复用中间研究结果；结合 Embedding 相关性筛选、TextRank 关键句提取与分级压缩，在上下文预算内组织证据，并保留来源关联。
- **证据审查与定向修复：** 设计 Red-Blue 审查机制，定位报告中的事实及引用问题，通过补充检索、定向修改或移除无依据结论完成修复；记录问题、证据与修改前后内容，通过轮数及调用预算限制无效迭代。
- **对照评测与可靠性验证：** 构建 ResearchBench 研究任务评测集及依赖失败、超时等离线回归场景，在统一模型、工具和预算条件下对比固定检索流程与 DAG 编排，开展压缩及审查模块消融，结合证据支持、修复正确性、耗时与 token 用量评估设计取舍。
