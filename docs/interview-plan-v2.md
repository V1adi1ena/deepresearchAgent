## 执行版（v3，按评审意见重写）

上一版执行版把范围缩成"修指标 + 跑 5 题"，与 L1–L4 及目标简历冲突，已作废。修指标只解决"可验证"，解决不了"机制没打通"；两者不能互相替代。

### 三条不可让渡的原则

1. **修指标 ≠ 修机制。** 支撑简历条目的 L1/L2/L3 实现必须做（依赖上下文注入、重规划保留结果、全局超时有界收尾、压缩接入真实增长边界）。实验规模可以缩，机制不能省。
2. **机制条目要行为验证，不是计数。** 编排的关键用例包括：A 的结果确实进入 B 的提示词；重规划没有重跑已成功任务；超时后的结果没有回流到证据。压缩与审查另按 L2/L3 验收。pytest 用例总数不是验收标准。
3. **"跑出报告" ≠ "任务成功"。** 至少三项核对：是否取得有效证据、是否回答了问题、引用是否支持主要结论。报告长度和子任务 SUCCESS 不能单独作为成功判据。

### 指标口径（按评审第 4 点收敛）

- `fact_accuracy` 更名为 **`reference_fact_match`（参考事实匹配）**，明确不声称事实正确性。
- 判定：在明确支持的表达模板内，检查实体与值的对应关系、否定修饰及数值口径。同一分句共现只是候选条件，不能直接判对；例如参考为“A=10、B=20”，报告为“A=20、B=10”必须判错。数值容差按题目预先定义，不因答案不同临时调整。
- 明确局限：不支持的同义改写、单位换算或隐含推理按预先声明的规则记为未匹配或无法判断，并保留原因；不声称具备通用事实判断能力。参考事实应补记来源和适用日期，未核验的参考事实不用于质量结论。
- 引用分两层核对：`citation_traceability` 只表示报告引用能对应到本次实际检索来源；“来源内容支持该结论”另行标注与检查。来源存在不等于结论正确。

### 顺序（采纳评审给出的顺序）

1. 修入口、数据隔离和指标，用离线用例验证
2. 跑 **1 题**确认真实外部链路（配额、工具参数、模型返回格式、耗时），这一步不作为后续改造已完成的证明
3. 修复 L1/L2/L3 中支撑简历的部分
4. 每个机制补最小行为验证
5. 在改造后的版本上跑 5 题链路检查，再从现有 35 题固定抽 3–5 题做小批对照，保留失败样本
6. 更新简历

### 前置硬约束：测试必须隔离数据目录

原脚本 `tests/continuous_test.py` 的 `clean_env()` 会删除 `data/memory.db` 和 `outputs/reports/report_*.md`。该脚本已有工作区改动，执行前需验证隔离确实生效，而非仅修改了入口名称。测试必须使用临时 SQLite、独立输出目录和唯一 session_id；清理前检查解析后的绝对路径位于本次测试目录内。真实模型 smoke test 与离线回归都不得清理原有记忆库或历史报告。

### 消融口径

开关没有改变执行路径时，两组差异可能来自模型或外部检索变化，不能归因于关闭了某个模块。处理：接上记忆与压缩开关，用离线调用记录验证“关闭后没有相关调用”；本轮不强制跑真实模型消融。简历可在该验收通过后写“开关控制模块接入”，不写未经对照验证的消融收益。固定流程与 DAG 的小批对照仍按 L4 执行。

### 费用与工时

各阶段按验收推进，不承诺固定半天或几小时完成。先在 1 题实测里记录模型、输入输出 token、调用次数与耗时，再按同一配置估算后续成本；审查、重试与输出长度会改变估算。截断、语义筛选和 TextRank 对照可在已安装的本地 embedding 模型下运行，不调用付费 LLM；若启用远程摘要、审查或补检，则单独记录其调用与费用。

### 简历上能用的，是"链路事实"

当前代码已核对有 35 道自建题、35 个不同 ID。题目数量说明题库规模，不证明参考答案已验证或系统效果。平均耗时、子任务数、检索次数和完成率只描述实际运行样本，须同时说明模型、配置、样本量和成功判据。保留率、检出率、误修改率在完成对应对照后才填写；量化可选，L2/L3 的机制行为验收不能省略。

### 这一步不做

不新建题库；不做显著性检验；不接 FastAPI / 断点续跑；不升级冲突检测；不承诺通用事实判断。

## 边界（两个诉求分开处理）

| 诉求 | 处理方式 |
| --- | --- |
| 写进简历的机制，当前尚未做到 | 可以。前提是该机制在投递前真正实现，并且能解释设计取舍与失败路径。本方案按"简历条目反推实现"来排期 |
| 尚无测评数据 | 先写机制，数字按下文“数字记录与使用”补充；未测出的数字直接省略，不影响先确定目标简历 |

目标是让每条简历描述都能对应具体实现、行为验证和可解释的取舍。代码位置、日志和复跑命令用于支撑回答，不以定位速度或数字数量作为验收标准。

## 阶段安排（按依赖与面试价值推进）

原计划 P0→P4 的骨架保留：每阶段先完成最小行为验证，再选择是否补充量化；L4 使用现有题库做小批对照，不另建大题库、不做显著性结论；增加 L0.5 提前检查外部链路，L1–L3 改造后仍需重新运行。

### L0：入口、数据隔离与评测口径（必须做）

先让运行与指标可核验。已有改动可以复用，但只有完成以下验收后才记为完成。

- [ ] 明确实际使用的评测入口。`evaluation/metrics.py` 与 `evaluation/metrics/` 存在重复指标逻辑；原审查时 `src/core/ablation.py` 用 `1.0` 占位。检查调用方后确定有效实现，不将占位分数输出为质量结果，不为整理入口顺手删除无关代码。
- [ ] 将 `fact_accuracy` 迁移为范围明确的 `reference_fact_match`，并同步调用方；覆盖错值、实体和值交换、否定和正确内容。引用存在与引用支持另测，不由关键词匹配替代。
- [ ] 统一当前指标字段与权重。原审查时 `factual_accuracy_str/_sem` 与权重字段不匹配，导致全满分输入得到 0.75；复验已有修改，必需字段缺失时明确失败，不静默计 0。
- [ ] 复验 embedding 降级处理。原审查时 `Embedder` 加载失败会退到 hash 随机向量，而语义指标仍输出正常分数。降级时抛错或标记 `embedding_backend=random` 并禁用相关指标，禁止该分数进入效果结论。
- [ ] 验证 README 单条命令与测试入口实际可用，记录解释器、依赖安装与运行步骤，不将本机绝对路径写成唯一可用的安装方式。
- [ ] 验证测试数据库、输出和清理都处于独立目录；可用临时目录内的样例文件验证清理边界，不能用真实历史文件试删。
- [ ] 将关键反例和开关调用验证写成可离线执行的 pytest 用例；保留每个用例检验的行为，数量不是完成标准。

验收：错值和实体错配不会仅因关键词共现而得分；测试确实覆盖声明的行为；入口可用；清理不越界；关键指标缺字段或语义后端不可用时明确失败或禁用，不能输出可误读的正常分数。

### L0.5：一次真实外部链路检查（必须做）

本次文档修订没有复跑真实模型。先检查模型与搜索通道的配额、返回格式及工具参数，避免后续计划依赖未经验证的外部链路；已有真实运行记录须核对对应版本和配置。

- [ ] 使用隔离数据库和输出目录，选 1 道题、明确的模型及真实搜索，记录版本、配置、trace、工具调用次数、token、耗时和失败原因。
- [ ] 在 `docs/runs/` 保存配置、运行摘要和原始产物位置；该记录只说明本次配置下的链路情况，不推断改造后的效果或平均指标。

### L1：编排、依赖数据流与容错（核心）

- [ ] 每层结束即发布结果到共享状态，下游启动前构建依赖上下文。原审查时 `result:{id}` 在 `_do_collecting` 才写入，而 `_build_task_context` 在 dispatch 阶段读取；依赖顺序并未形成跨层结果传递。同层按定义应相互独立。
- [ ] 统一依赖键约定。原审查时 `context_keys` 由模型自由生成，与编排器的 `dep:{task_id}` 无一致约定。由代码根据已校验的 dependencies 确定性注入结果；固定 schema 可用于提示词和日志，但不能仅靠模型正确填写 context_keys 才让依赖生效。
- [ ] 明确上游失败后的阻断 / 降级 / 重规划规则，避免错误信息作为证据传播。
- [ ] 重规划保留成功结果，最终合成同时使用保留结果与新结果。原审查时 `_do_replanning` 直接清空 `_results`，需验证保留结果的实际使用路径。
- [ ] 区分"有界重试（临时故障）"与"重规划（方案需变）"，预算内不得无限叠加。
- [ ] 修复全局超时收尾。原审查时置为 SYNTHESIZING 后立刻 `break`，没有执行合成。先定义总期限和收尾预算：剩余预算内可合成部分报告，无可用预算时直接返回已收集结果和中断原因，不能为合成无限延长总期限；标记未完成子任务。
- [ ] 超时与取消的边界：`asyncio.wait_for` 取消的是协程，底层模型调用跑在 `asyncio.to_thread` 线程池里仍在跑。明确"晚到结果丢弃并记录"，不允许污染证据链。
- [ ] 作用域与幂等：结果标识用 session/run/task 三级作用域，检查不同 run 复用 task_id 时 SQLite 覆盖。

验收：A 的特定输出出现在依赖它的 B 的实际提示词里；重规划不重复执行成功任务，且最终报告仍能使用其结果；部分成功、全失败、阶段超时和全局超时各有行为用例。并发验证区分调度中的任务数与底层未完成请求数，不能用协程数证明超时线程已停止；晚到结果不回流证据链。

### L2：共享记忆与上下文压缩（机制必须验证，量化可选）

- [ ] 记忆写入、检索、复用的时机明确；接入 researcher 的上下文组装边界。原审查时语义记忆主要在 planning 阶段检索，需验证子 Agent 真正收到相关内容。
- [ ] 压缩接到真实的上下文增长边界。原审查时调用位于规划上下文回退分支，不能单凭压缩器存在宣称研究过程使用了压缩。
- [ ] 压缩时保留"任务—来源—摘录"关联，保证下游结论可追溯；处理消息时保持 tool_calls 与 tool result 的协议配对。
- [ ] 语义去重保留误合并检查，高相似度 ≠ 同一事实。
- [ ] 最小行为验证：固定文档、干扰文本与标注证据，检查压缩确实发生，保留的内容及其来源能够进入下游任务；记录必要证据丢失的边界。
- [ ] 可选量化：在同一预算和同一文档集上比较截断、相关性筛选、加入 TextRank 的保留率与压缩比。以上可用本地 embedding 运行；若对比分级摘要，另计 LLM 调用及费用。

验收：实际增长边界使用了所选策略，能指认保留和丢弃的证据，下游仍能追溯来源。机制验收不以是否有百分比为条件；只有实测三策略对照后，才能填写相应保留率和压缩比。

### L3：基于证据的 Red-Blue 审查（机制必须验证，量化可选）

- [ ] 只针对可核对的问题输出结构化结果：定位、问题类型、证据。
- [ ] 补检来源进入统一来源记录，修复后引用能对应到实际检索内容。
- [ ] 保留修改前后内容与依据；补检失败时允许删除结论或标注不确定，不强制生成确定答案。
- [ ] 评分与修改记录绑定实际报告版本，不将修改前的审查得分记成修改后报告的质量。
- [ ] 轮数与调用预算限制无效迭代；不拿模型自评置信度当事实正确的证明。
- [ ] 最小行为验证：覆盖明确错值、无依据引用和正确内容，保留审查、补检、修复与核对记录；离线 fixture 可验证流程，不能代替真实模型的发现或修复能力。
- [ ] 可选量化：在上述标注样本上逐项统计检出、修复与误修改。人工准备样本和指标计算可离线完成，真实 Red-Blue 与补检调用按实际后端记录用量和费用。

验收：有一条完整“错误 → 定位 → 补检 → 修改 → 核对”记录，以及证据不足或补检失败时的处理记录；检查正确内容是否被改坏。实际误修改如实保留，未观察到时说明样本量与局限，不制造失败或声称普遍无误修改。

### L4：改造后的链路检查与最小对照

复用已有 35 题，不另建大题库。控制本轮样本与调用规模，报告逐题结果，不做统计显著性或普遍性能结论。

- [ ] 在 L1–L3 改造后的版本上运行 5 道真实题，区分是否取得有效证据、是否回答问题、引用是否支持主要结论；失败结果也保留，长度和 SUCCESS 不单独作为成功判据。
- [ ] 从现有 35 题固定抽取 3–5 题做固定检索后合成与 DAG 编排的小批对照，统一模型、工具可用范围和预算上限，并记录实际开销。用于调参的题与用于描述结果的题分别标识；若复用了同一组，明确这是开发集结果。
- [ ] 问题级记录：报告、trace、完成情况、证据支持、修复正确性、耗时、token、失败原因。
- [ ] 保留失败样本与故障说明，不把实验故障写成生产事故。
- [ ] 不设“超过 20 题即可做显著性结论”的硬阈值。当前只描述本设置下观察到的差异；以后扩大结论时另行设计采样、重复运行和不确定性分析。

验收：5 题链路检查和小批对照均有问题级记录，成功判据明确，失败样本未被排除；简历中的数字能定位到具体配置、样本和记录。L4 不依赖可选的完整消融或收益百分比。

### 明确不做

FastAPI / SSE / 任务平台 / 断点续跑 / 自进化 / 训练 / 多模态 / 冲突检测升级。与需求无关，且挤压上面的时间。

## 数字的来源与使用条件

| 类型 | 例子 | 获取成本 | 说明 |
| --- | --- | --- | --- |
| 结构性事实 | 实际可用工具数、状态数、并发上限、DAG 层数、测试用例数 | 代码与配置核验 | 不能用数量替代功能正确性或效果 |
| 本地对照指标 | 压缩比、标注证据保留率、去重误合并、指标反例结果 | 本地计算与标注时间；预先准备语义模型 | 明确数据、策略、预算、计算口径和局限 |
| 真实模型与工具指标 | 审查检出 / 修复 / 误修改率，端到端 token、耗时、调用次数、样本完成率 | 按实际配置和用量记录 | 模拟或回放不能冒充真实模型效果；均值与比例须有样本和分母 |

## 数字记录与使用

1. 每个数字记录版本、模型、配置、样本、计算口径与原始结果位置；实际 token 和估算 token 分别标注。
2. 未做对照时，只描述运行事实，不写“提升”或归因于某个模块。
3. 数字可省略，行为验证不可省略。小样本和开发集结果明确标注，不推广到生产效果。
4. 对正确内容的误修改率、失败样本与额外开销同样记录，不能只选有利结果。

| 重规划保留成功结果 | `_do_replanning` 改造 | 重试和重规划怎么区分？会不会无限重规划？ | 重试解决临时故障（次数有界），重规划解决方案变化（轮数有界）；给出预算耗尽的收尾行为 |
| 全局超时收尾 | 超时用例 | 超时后还在跑的调用怎么办？ | 区分协程与底层请求；晚到结果不回流。解释总期限、收尾预算及没有预算时的部分结果返回 |
| 共享记忆 + 语义去重 | SQLite/NumPy + 检索路径 | 为什么不直接拼上下文？相似度多少算重复？ | 预算有限 + 跨 Agent 复用；给出阈值与误合并的实测样例 |
| 分级压缩与 TextRank | 三策略对照 | 为什么不用直接截断？怎么知道重要信息没丢？ | 截断按位置丢尾部证据；用 gold fact 保留率量化；给出失败案例 |
| Red-Blue 审查与定向修复 | 植入错误集 | 两个 Agent 会不会互相附和？多轮增加多少成本？ | 审查限定可核对项、发现问题须带证据；轮数/调用预算；给出误修改案例 |
| 评测口径修正 | 反例集 + pytest | 关键词命中为什么不算事实正确？ | 举否定、错值和实体错配反例；解释参考事实匹配的模板边界，以及引用可追溯与内容支持的区别 |
| 对照实验结论 | L4 问题级记录 | 基线怎么设的？样本多少？结论能推广吗？ | 说明自建题、统一预算、样本小、只能说明本设置下的差异 |

## 建议补的一件事：离线可演示

可复用离线用例或明确标记的 LLM/工具 fixture 演示规划、调度、合成与审查，并输出 trace。使用独立测试目录，不另建演示平台。回放用于说明流程和失败处理，真实检索、模型效果及成本仍以真实运行记录为准；代码中存在额度错误处理不等于已发生过某次真实故障。
